PHẦN VII · FISHNET

Prediction v2: Rollback Netcode trong FishNet

Đây là tính năng được cộng đồng FishNet coi là "con át chủ bài": Prediction v2. Nó hiện thực hóa gần như đầy đủ bộ lý thuyết Client-Side Prediction + Server Reconciliation đã học ở chương 5 — cùng tinh thần với Prediction/Reconciliation của Photon Fusion (chương 30) — nhưng khác biệt lớn nhất là FishNet miễn phí và mã nguồn mở hoàn toàn, không tính phí theo CCU (Concurrent Users — số người chơi đồng thời) như Fusion. Chương này giải thích cơ chế hoạt động bên trong, yêu cầu bắt buộc về tính xác định (determinism), và đặt Prediction v2 vào bức tranh rộng hơn của kỹ thuật Rollback Netcode nổi tiếng trong giới game đối kháng.

1. Vì sao cần Prediction, nhắc nhanh từ chương 5

Chương 5 đã giải thích: nếu Client gửi input di chuyển lên Server rồi ngồi chờ Server tính toán và gửi lại vị trí mới, nhân vật sẽ "khựng" lại đúng bằng độ trễ round-trip (RTT — Round-Trip Time, thời gian đi và về của một gói tin) — cảm giác điều khiển trở nên nặng nề, khó chịu. Giải pháp là Client-Side Prediction: Client tự chạy trước logic di chuyển ngay khi nhận input, hiển thị kết quả ngay lập tức mà không đợi Server; sau đó khi Server phản hồi trạng thái "thật", Client so sánh và tự sửa (Server Reconciliation) nếu có sai lệch. FishNet Prediction v2 là bản đóng gói sẵn toàn bộ quy trình này thành API, để lập trình viên không phải tự viết từ đầu cơ chế lưu lịch sử input, so khớp tick, và resimulate như khi tự chế (chương 11 đã từng đề cập việc tự chế giao thức ở tầng thấp hơn).

2. Cơ chế hoạt động bên trong Prediction v2

Prediction v2 xoay quanh việc đánh dấu các hàm cần chạy theo đúng nhịp tick cố định (fixed tick, khái niệm Tick Rate đã học ở chương 4) bằng các callback đặc biệt do NetworkBehaviour cung cấp, tiêu biểu là RunInputs() (thu input) và RunInputs/OnTick kết hợp cùng khối mô phỏng vật lý riêng. Khi được cấu hình đúng, FishNet tự động thực hiện bốn bước sau cho mỗi tick:

  1. Chạy dự đoán ngay lập tức (Predict): Ngay khi Client thu thập input của người chơi ở tick hiện tại, FishNet chạy ngay hàm mô phỏng (ví dụ di chuyển nhân vật theo input đó) tại chỗ trên Client, hiển thị kết quả lên màn hình lập tức — không đợi phản hồi Server.
  2. Lưu lại lịch sử (Cache input & state): FishNet tự động lưu lại cả input đã dùng và trạng thái (state) kết quả sau khi mô phỏng, gắn với đúng số hiệu tick đó, vào một bộ đệm lịch sử nội bộ.
  3. Nhận state thật từ Server và so sánh: Server, với vai trò authoritative, cũng chạy đúng mô phỏng đó (thường trễ hơn Client một khoảng round-trip) rồi gửi trạng thái kết quả kèm số hiệu tick về Client. Khi Client nhận được, nó tra lại đúng trạng thái đã lưu ở tick tương ứng trong lịch sử và so sánh hai giá trị.
  4. Reconcile nếu khác nhau (Rollback + Resimulate): Nếu trạng thái Server gửi về khác với trạng thái Client đã dự đoán tại đúng tick đó (do gói tin input bị mất, do Server bác input vì lý do hợp lệ hóa, hoặc do có Client khác tương tác gây thay đổi mà Client này chưa biết), FishNet sẽ: (a) đưa Client "lùi lại" (rollback) về đúng trạng thái Server vừa gửi tại tick đó, sau đó (b) resimulate — chạy lại tuần tự toàn bộ các tick sau đó cho tới tick hiện tại, dùng chính các input đã lưu trong lịch sử — để một lần nữa suy ra trạng thái hiện tại, lần này khớp đúng với những gì Server sẽ đồng ý.

C# Skeleton toi thieu su dung Prediction v2

using FishNet.Object;
using FishNet.Object.Prediction;
using UnityEngine;

public struct MoveInputData : IReplicateData
{
    public float Horizontal;
    public float Vertical;
    private uint _tick;
    public void Dispose() { }
    public uint GetTick() => _tick;
    public void SetTick(uint value) => _tick = value;
}

public struct MoveReconcileData : IReconcileData
{
    public Vector3 Position;
    public Quaternion Rotation;
    private uint _tick;
    public void Dispose() { }
    public uint GetTick() => _tick;
    public void SetTick(uint value) => _tick = value;
}

Ý nghĩa hai struct: IReplicateData đóng gói đúng những gì cần để mô phỏng lại một tick — thường là input thô của người chơi. IReconcileData đóng gói trạng thái kết quả cần so sánh/khôi phục — thường là vị trí, hướng xoay, vận tốc. FishNet dùng số hiệu tick lưu trong mỗi struct để khớp chính xác dữ liệu dự đoán với dữ liệu thật từ Server.

2.1 Đăng ký vòng lặp tick

Hai struct ở trên chỉ là "khuôn dữ liệu"; để FishNet thực sự gọi đúng hàm mô phỏng (RunInputs) và hàm khôi phục (OnReconcile) vào đúng nhịp tick, cần đăng ký chúng với TimeManager — thành phần con của NetworkManager đã giới thiệu ở chương 38, chịu trách nhiệm phát tín hiệu tick đều đặn theo Tick Rate cấu hình sẵn (khái niệm Tick Rate đã học lý thuyết ở chương 4).

C# Dang ky Replicate/Reconcile trong OnStartNetwork
public override void OnStartNetwork()
{
    base.OnStartNetwork();
    // Dang ky de FishNet tu goi RunInputs()/OnReconcile() theo dung tick,
    // huy dang ky tuong ung trong OnStopNetwork() de tranh memory leak
    TimeManager.OnTick += TimeManager_OnTick;
}

public override void OnStopNetwork()
{
    base.OnStopNetwork();
    TimeManager.OnTick -= TimeManager_OnTick;
}

private void TimeManager_OnTick()
{
    // Thu input cua nguoi choi (chi co y nghia tren client la Owner)
    if (IsOwner)
    {
        MoveInputData input = new MoveInputData
        {
            Horizontal = Input.GetAxisRaw("Horizontal"),
            Vertical = Input.GetAxisRaw("Vertical")
        };
        RunInputs(input);
    }
}

Bên trong FishNet, việc đánh dấu RunInputs là một "Replicate method" và OnReconcile là một "Reconcile method" thường được thực hiện qua attribute hoặc qua đăng ký tường minh với PredictionManager, tùy phiên bản framework — điểm mấu chốt cần nhớ là cả hai hàm này luôn phải được gọi đúng theo tick, không được gọi tùy tiện trong Update() (vốn chạy theo từng frame hiển thị, tần suất không cố định và không khớp với tick mô phỏng).

2.2 Khi gói tin input bị mất trên đường truyền

Input của người chơi được gửi qua kênh Unreliable tốc độ cao (khái niệm Channel đã học ở chương 40) để giảm độ trễ tối đa — nhưng điều đó đồng nghĩa một vài gói input hoàn toàn có thể bị rớt dọc đường, đặc biệt khi mạng có tỷ lệ mất gói cao (chương 2 đã học khái niệm Packet Loss). Khi Server phát hiện thiếu input đúng tick mong đợi từ một Client, FishNet không đơn thuần "bỏ qua tick đó" — hành vi mặc định là dùng lại (redundant hoặc tái sử dụng) input gần nhất đã nhận được để mô phỏng tạm cho tick bị thiếu, giảm thiểu cảm giác khựng đột ngột. Đây là lý do một khoảng mất gói ngắn thường không gây giật rõ rệt, trong khi mất gói kéo dài liên tục nhiều tick mới bắt đầu gây sai lệch rõ giữa dự đoán Client và trạng thái Server, dẫn tới reconcile lớn hơn bình thường.

3. Yêu cầu bắt buộc: Determinism (tính xác định)

Toàn bộ cơ chế resimulate ở bước 4 chỉ đúng nếu chạy lại cùng một input qua cùng một hàm mô phỏng luôn cho ra cùng một kết quả, bất kể chạy bao nhiêu lần, ở máy nào, vào thời điểm nào. Đặc tính này gọi là Determinism (tính xác định) — đây là yêu cầu sống còn của mọi hệ thống rollback, không riêng gì FishNet.

Cảnh báo vi phạm Determinism — nguyên nhân phổ biến nhất gây "giật, nhảy" khi dùng Prediction v2:
  • Random không đồng bộ seed: Gọi Random.Range() (hoặc bất kỳ nguồn ngẫu nhiên nào) trực tiếp bên trong hàm mô phỏng mà không cố định seed theo đúng tick sẽ khiến mỗi lần resimulate cho ra một kết quả khác nhau — nhân vật có thể "dạt" sang một vị trí hơi khác mỗi lần Server reconcile, gây hiện tượng giật hình rõ rệt. Nếu cần yếu tố ngẫu nhiên trong logic dự đoán (ví dụ độ lệch bắn súng), phải dùng một bộ sinh số giả ngẫu nhiên (PRNG) được seed cố định theo đúng số hiệu tick.
  • Phụ thuộc thời gian hệ thống trực tiếp: Dùng Time.time, DateTime.Now, hoặc bất kỳ đồng hồ hệ thống thực nào bên trong hàm mô phỏng thay vì dùng đúng giá trị delta-time cố định của một tick sẽ phá vỡ tính lặp lại — hai lần chạy cùng một tick ở hai thời điểm khác nhau (lần đầu dự đoán, lần sau resimulate) sẽ cho kết quả khác nhau.
  • Đọc trạng thái ngoài phạm vi được resimulate: Hàm mô phỏng đọc một biến toàn cục/singleton nào đó đã bị thay đổi bởi luồng logic khác (không thuộc hệ thống Prediction) giữa lần predict đầu tiên và lần resimulate sau này cũng gây ra kết quả không nhất quán.
  • Thứ tự lặp không cố định: Dùng Dictionary/HashSet (thứ tự duyệt không đảm bảo) ở nơi logic phụ thuộc thứ tự xử lý, thay vì cấu trúc có thứ tự cố định như mảng/List.
Nguyên tắc chung: mọi thứ hàm mô phỏng cần để tính ra kết quả phải nằm gọn trong tham số input + state đã lưu của đúng tick đó — không được "rò rỉ" thêm bất kỳ nguồn dữ liệu ngoài luồng nào khác.

4. Rollback Netcode trong bức tranh rộng hơn: GGPO và Lockstep

Kỹ thuật "lùi lại - chạy lại" (rollback - resimulate) mà Prediction v2 dùng cho di chuyển nhân vật trong game hành động/bắn súng thực chất chính là ý tưởng cốt lõi đứng sau GGPO — thư viện rollback netcode nổi tiếng khởi nguồn từ giới game đối kháng (fighting game), giúp các tựa game như vậy chơi mượt qua mạng dù độ trễ cao, bằng cách luôn dự đoán input đối thủ, chạy tiếp game ngay, rồi rollback toàn bộ nhiều frame và resimulate khi biết input thật sai với dự đoán. FishNet đã mang đúng triết lý đó vào một middleware Unity đa dụng, áp dụng được cho nhiều thể loại game chứ không chỉ riêng đối kháng.

Forward-reference chương 49: Chương 49 (Lockstep, Rollback & Deterministic Simulation) sẽ đi sâu hơn vào kiến trúc tổng quát của các mô hình mô phỏng đồng bộ theo tick — bao gồm so sánh Lockstep (mọi máy đợi nhau, cùng mô phỏng input giống hệt nhau, thường dùng cho game chiến lược thời gian thực - RTS) với Rollback (không đợi, luôn dự đoán rồi sửa sai khi cần, thường dùng cho game hành động/đối kháng nhạy độ trễ). Prediction v2 của FishNet chính là một hiện thực cụ thể, đóng gói sẵn của nhánh Rollback này, áp dụng ở quy mô một object/nhân vật thay vì toàn bộ trạng thái trận đấu như GGPO nguyên bản.

Thực hành chuẩn là chỉ chạy predict đầy đủ cho object mà Client hiện tại là Owner (chính nhân vật mình điều khiển); với nhân vật người chơi khác, chỉ cần nội suy mượt theo state Server gửi về — không cần đoán trước hành vi của họ vì Client không có input của họ để mà dự đoán chính xác.

Tổng kết chương

Prediction v2 là điểm khác biệt lớn nhất giúp FishNet được xem trọng ngang hàng các middleware thương mại: nó tự động hóa toàn bộ chu trình dự đoán - lưu lịch sử - so sánh - rollback - resimulate mà lẽ ra lập trình viên phải tự tay xây dựng nếu tự chế netcode ở tầng thấp. Điều kiện tiên quyết để cơ chế này hoạt động đúng là logic mô phỏng phải hoàn toàn deterministic — tránh random không seed cố định, tránh phụ thuộc đồng hồ hệ thống, tránh đọc trạng thái ngoài phạm vi input/state đã lưu. Về bản chất, đây chính là kỹ thuật Rollback Netcode nổi tiếng từ GGPO trong giới game đối kháng, được FishNet đóng gói lại cho hệ sinh thái Unity — chương 49 sẽ mở rộng góc nhìn này lên tầm kiến trúc tổng quát (Lockstep vs Rollback). Chương 42, chương cuối của Phần VII, sẽ ghép toàn bộ kiến thức từ chương 38 tới đây thành một ví dụ thiết lập FishNet hoàn chỉnh từ đầu.
