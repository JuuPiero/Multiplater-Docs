PHẦN V · PHOTON FUSION 2

Ví dụ: chuyển đổi tư duy từ PUN sang Fusion

Chương khép lại Phần V này tổng hợp lại toàn bộ kiến thức Fusion đã học (chương 26–30) thành một bảng mapping trực tiếp với các khái niệm PUN quen thuộc (Phần IV), giúp người đã thành thạo PUN rút ngắn thời gian học Fusion. Sau bảng mapping là một ví dụ code song song cho cùng một tác vụ — đồng bộ vị trí nhân vật — viết theo cả hai phong cách, và kết thúc bằng lời khuyên thực tế: khi nào nên ở lại với PUN, khi nào nên đầu tư học Fusion ngay từ đầu dự án.

1. Bảng mapping khái niệm: PUN ↔ Fusion

PUN (Phần IV)Fusion (Phần V)Ghi chú khác biệt quan trọng
PhotonViewNetworkObject + NetworkBehaviourFusion tách thành hai lớp: NetworkObject đại diện cho định danh mạng của cả GameObject, còn mỗi NetworkBehaviour là một script logic riêng gắn trên đó (chương 28)
photonView.IsMineObject.HasInputAuthorityKhông hoàn toàn giống 100% về ngữ nghĩa — Fusion phân biệt rạch ròi Input Authority (ai gửi input) và State Authority (ai quyết định kết quả), trong khi PUN gộp chung mơ hồ vào một khái niệm "Owner" (chi tiết đã giải thích ở chương 29)
[PunRPC] + photonView.RPC(...)[Rpc(RpcSources.X, RpcTargets.Y)]Fusion khai báo nguồn/đích ngay tại định nghĩa hàm thay vì chỉ định target lúc gọi (chương 29)

2. Ví dụ song song: đồng bộ vị trí nhân vật

Đoạn code dưới đây minh họa cùng một tác vụ — gửi vị trí nhân vật do chính người chơi điều khiển cho các client khác — viết theo cả hai phong cách, để thấy trực quan sự khác biệt cú pháp và triết lý.

C# Phong cách PUN — tự tay tuần tự hóa qua OnPhotonSerializeView
using Photon.Pun;
using UnityEngine;

public class PlayerMovePun : MonoBehaviourPun, IPunObservable
{
    private Vector3 networkPosition;

    void Update()
    {
        if (photonView.IsMine)
        {
            // Nguoi choi dieu khien truc tiep tren may cua chinh minh
            float h = Input.GetAxis("Horizontal");
            float v = Input.GetAxis("Vertical");
            transform.position += new Vector3(h, 0, v) * Time.deltaTime * 5f;
        }
        else
        {
            // May khac: tu lam muot toi vi tri nhan duoc tu mang
            transform.position = Vector3.Lerp(transform.position, networkPosition, Time.deltaTime * 10f);
        }
    }

    // Phai tu tay quy dinh du lieu nao gui di, du lieu nao nhan ve
    public void OnPhotonSerializeView(PhotonStream stream, PhotonMessageInfo info)
    {
        if (stream.IsWriting)
        {
            stream.SendNext(transform.position);
        }
        else
        {
            networkPosition = (Vector3)stream.ReceiveNext();
        }
    }
}
Photon Phong cách Fusion — khai bao [Networked], Fusion tu dong lo phan con lai
using Fusion;
using UnityEngine;

public class PlayerMoveFusion : NetworkBehaviour
{
    // Khong can tu viet SendNext/ReceiveNext - Fusion tu dong dong bo
    [Networked] public Vector3 Position { get; set; }

    public override void FixedUpdateNetwork()
    {
        if (GetInput(out PlayerNetworkInput input))
        {
            Vector3 move = new Vector3(input.MoveDirection.x, 0, input.MoveDirection.y);
            // Logic nay tu dong duoc Fusion predict tren client
            // va rewind/re-simulate khi can (chuong 30) - khong can code them
            Position += move * 5f * Runner.DeltaTime;
        }

        transform.position = Position;
    }
}
Điểm khác biệt cốt lõi lộ ra qua ví dụ: Ở PUN, lập trình viên phải tự quyết định "gửi gì, nhận gì" trong OnPhotonSerializeView, và tự viết logic làm mượt (Lerp) cho các máy không sở hữu object — đây chính là một dạng interpolation thủ công. Ở Fusion, chỉ cần khai [Networked], và cả hai việc — đồng bộ dữ liệu lẫn làm mượt cho máy khác — đều được framework tự động đảm nhiệm theo đúng cơ chế đã học ở chương 30, kể cả prediction cho chính người chơi lẫn interpolation cho người chơi khác.

3. Vậy có nên chuyển từ PUN sang Fusion không?

Câu trả lời phụ thuộc vào bối cảnh dự án, không có đáp án đúng tuyệt đối cho mọi trường hợp:

KHÔNG nhất thiết phải chuyển đổi nếu: Dự án đang dùng PUN và chạy ổn định cho quy mô nhỏ/casual — chi phí học lại toàn bộ tư duy tick-based cộng với chi phí refactor codebase hiện có sang Fusion là không nhỏ, và nếu game của bạn không thực sự cần chống gian lận nghiêm ngặt hay cảm giác điều khiển siêu mượt, khoản đầu tư đó có thể không mang lại lợi ích tương xứng.
NÊN cân nhắc Fusion ngay từ đầu cho dự án MỚI nếu cần:
  • Chống gian lận nghiêm túc — nhờ mô hình Client-Server Mode với State Authority là server thật (chương 27, 28).
  • Cảm giác điều khiển mượt mà bất chấp độ trễ — nhờ Prediction/Reconciliation tích hợp sẵn, không cần tự viết tay (chương 30).
  • Quy mô CCU (Concurrent Users — số người dùng đồng thời) lớn hơn đáng kể so với những gì gói miễn phí/giá thấp của PUN có thể đáp ứng thoải mái.
