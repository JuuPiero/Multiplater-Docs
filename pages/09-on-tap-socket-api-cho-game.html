PHẦN II · LẬP TRÌNH SOCKET CHO GAME

Ôn tập Socket API cho Game: TCP/UDP trong C++

Chương này không dạy lại socket(), bind(), sendto(), recvfrom() từ đầu — bộ tài liệu "Mạng máy tính & Lập trình Socket" (chương 6-16) đã trang bị đầy đủ. Thay vào đó, chương này xoáy sâu vào ba điểm khác biệt sống còn khi áp dụng đúng bộ API đó cho một game realtime: bắt buộc dùng non-blocking mode, hiểu đúng vai trò của địa chỉ nguồn trong recvfrom() để phân biệt hàng trăm người chơi qua một socket UDP duy nhất, và cấu trúc lại toàn bộ vòng lặp chính (game loop) để nó không bao giờ bị chặn bởi I/O mạng. Đây là nền tảng bắt buộc trước khi bước vào thiết kế giao thức nhị phân ở chương 10.

1. Vì sao Non-blocking Mode là bắt buộc cho Game Server/Client

Ở chế độ mặc định (blocking), khi gọi recvfrom() mà chưa có gói tin nào tới, hàm sẽ "đứng chờ" (block) — dòng lệnh đó không trả về, các dòng lệnh phía sau không được thực thi — cho tới khi có dữ liệu xuất hiện. Với một chương trình xử lý tuần tự đơn giản (ví dụ ví dụ TCP echo ở chương 17-19 bộ tài liệu Mạng máy tính), đây là hành vi chấp nhận được, thậm chí tiện lợi.

Nhưng với một game loop thời gian thực, hành vi này gây ra thảm họa: mỗi khung hình (frame)/mỗi tick, chương trình còn cần tính vật lý, cập nhật AI, kiểm tra va chạm, và (ở phía client) render đồ họa lên màn hình — tất cả những việc này phải chạy đều đặn hàng chục lần mỗi giây bất kể mạng có dữ liệu hay không. Nếu recvfrom() ở chế độ blocking được gọi ngay đầu vòng lặp và không có gói tin nào tới trong một khoảng thời gian (ví dụ đối thủ tạm ngừng gửi, hoặc mạng nghẽn), toàn bộ vòng lặp game bị "treo cứng" tại đúng dòng lệnh đó — không tính vật lý được, không render được, người chơi thấy hình ảnh đứng hình hoàn toàn dù CPU vẫn còn dư thừa để làm mọi việc khác.

Hệ quả trực tiếp: Một game server dùng recvfrom() blocking sẽ không thể tick đều đặn cho tất cả người chơi khi vắng gói tin từ bất kỳ ai — toàn bộ simulation của mọi client khác cũng bị treo theo, dù họ đang gửi dữ liệu đều đặn. Đây là lý do non-blocking mode không phải một tùy chọn tối ưu, mà là điều kiện bắt buộc cho bất kỳ socket nào tham gia vào một game loop thời gian thực.

2. Chuyển Socket sang chế độ Non-blocking

Chuyển một socket đã tạo bởi socket() sang non-blocking là một thao tác một dòng, nhưng cú pháp khác nhau hoàn toàn giữa hai nền tảng.

Windows ioctlsocket()

int ioctlsocket(SOCKET s, long cmd, u_long *argp);
// cmd = FIONBIO, *argp = 1 (bat non-blocking) hoac 0 (tro ve blocking)

Ý nghĩa: Lệnh điều khiển I/O mức thấp FIONBIO ("File IOctl Non-Blocking I/O") bật/tắt chế độ non-blocking cho socket. Đây là cách đơn giản và phổ biến nhất trên Windows để chuyển một socket UDP hoặc TCP sang non-blocking ngay sau khi tạo.

Thay thế nâng cao — WSAEventSelect(): Winsock còn cung cấp WSAEventSelect(), gắn một socket với một event object của Windows, cho phép chương trình chờ đồng thời nhiều socket bằng WSAWaitForMultipleEvents() mà không cần bận rộn kiểm tra (poll) liên tục — hữu ích cho server có nhiều kết nối TCP, nhưng với một socket UDP đơn của game server, ioctlsocket() đơn giản và đủ dùng hơn nhiều. Cơ chế event-based nâng cao này sẽ được nhắc lại ở chương 13 khi bàn về I/O multiplexing.

Windows C++
u_long mode = 1;  // 1 = bat non-blocking
if (ioctlsocket(sock, FIONBIO, &mode) != 0) {
    fprintf(stderr, "ioctlsocket() that bai, ma loi: %d\n", WSAGetLastError());
}

Linux fcntl()

int fcntl(int fd, int cmd, ... /* arg */);
// doc co hien tai: fcntl(fd, F_GETFL, 0)
// dat co moi:      fcntl(fd, F_SETFL, flags | O_NONBLOCK)

Ý nghĩa: fcntl() ("file control") là hàm điều khiển thuộc tính của bất kỳ file descriptor nào trên POSIX, bao gồm cả socket (đúng theo triết lý Unix "mọi thứ đều là file" đã nhắc ở chương 9 bộ tài liệu Mạng máy tính). Để bật non-blocking an toàn, thực hành chuẩn là đọc trước tập cờ hiện có bằng F_GETFL, rồi ghi lại tập cờ đó cộng thêm bit O_NONBLOCK bằng F_SETFL — tránh vô tình xóa mất các cờ khác đã được thiết lập trước đó.

Linux C++
int flags = fcntl(sock, F_GETFL, 0);
if (flags == -1) {
    fprintf(stderr, "fcntl(F_GETFL) that bai: %s\n", strerror(errno));
} else if (fcntl(sock, F_SETFL, flags | O_NONBLOCK) == -1) {
    fprintf(stderr, "fcntl(F_SETFL) that bai: %s\n", strerror(errno));
}

Hàm gộp chung, dùng ngay trong mọi ví dụ code từ đây trở đi trong Phần II:

C++ — SetSocketNonBlocking() dung chung cho ca hai nen tang
#ifdef _WIN32
  #include <winsock2.h>
  #include <ws2tcpip.h>
  #pragma comment(lib, "Ws2_32.lib")
  using socket_t = SOCKET;
#else
  #include <sys/socket.h>
  #include <netinet/in.h>
  #include <arpa/inet.h>
  #include <unistd.h>
  #include <fcntl.h>
  #include <cerrno>
  using socket_t = int;
#endif
#include <cstdio>
#include <cstring>

bool SetSocketNonBlocking(socket_t sock) {
#ifdef _WIN32
    u_long mode = 1;
    return ioctlsocket(sock, FIONBIO, &mode) == 0;
#else
    int flags = fcntl(sock, F_GETFL, 0);
    if (flags == -1) return false;
    return fcntl(sock, F_SETFL, flags | O_NONBLOCK) != -1;
#endif
}

Xử lý đúng "lỗi giả": EWOULDBLOCK / EAGAIN

Khi một socket non-blocking chưa có dữ liệu để đọc, recvfrom() không chờ mà trả về ngay lập tức với giá trị lỗi (-1 trên cả hai nền tảng) — và mã lỗi cụ thể là WSAEWOULDBLOCK trên Windows, hoặc EWOULDBLOCK/EAGAIN trên Linux (theo POSIX, hai hằng số này có thể trùng giá trị hoặc khác nhau tùy hệ thống, nên luôn kiểm tra cả hai cho chắc chắn).

Đây KHÔNG phải một lỗi thật: Đây chỉ là cách hệ điều hành nói "hiện chưa có gì để đọc, đừng chờ, quay lại làm việc khác". Chương trình phải diễn giải mã lỗi này thành "chưa có gói tin nào — tiếp tục vòng lặp bình thường", chứ tuyệt đối không được coi đây là lỗi mạng thật sự và không được in cảnh báo, ngắt kết nối, hay thử kết nối lại. Quên xử lý riêng biệt trường hợp này — coi mọi giá trị trả về âm từ recvfrom() là lỗi nghiêm trọng — là lỗi phổ biến nhất khi mới chuyển từ blocking sang non-blocking socket.

3. recvfrom() và bài toán phân biệt Client qua Địa chỉ Nguồn

Khác biệt kiến trúc quan trọng nhất giữa TCP và UDP khi phục vụ nhiều client: với TCP, mỗi lần accept() trả về một socket phiên (session socket) hoàn toàn riêng cho từng client (đã học ở chương 9 bộ tài liệu Mạng máy tính) — chương trình biết ngay dữ liệu đọc được từ socket nào là của client nào, vì mỗi client có một "đường ống" socket vật lý riêng. Với UDP, hoàn toàn không có khái niệm này: một socket UDP server DUY NHẤT — được tạo một lần bằng socket() và bind() một lần vào một cổng cố định — có thể nhận gói tin từ hàng trăm client khác nhau cùng lúc, tất cả đều đi qua đúng một socket đó.

recvfrom() — vai trò của tham số địa chỉ nguồn

// Windows
int recvfrom(SOCKET s, char *buf, int len, int flags,
             struct sockaddr *from, int *fromlen);
// Linux
ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags,
                  struct sockaddr *src_addr, socklen_t *addrlen);

Điểm mấu chốt: Tham số from/src_addr — thường là một struct sockaddr_in đã memset về 0 — được hệ điều hành tự động điền địa chỉ IP và cổng (port) nguồn của gói tin vừa nhận, mỗi lần gọi recvfrom(). Đây chính là "chìa khóa" duy nhất để server phân biệt gói tin này đến từ ai: server so sánh cặp (IP, port) vừa nhận được với một danh sách/bảng ánh xạ nội bộ đã lưu, để biết đây là người chơi đã quen hay một client hoàn toàn mới cần khởi tạo dữ liệu.

Vì vậy, server phải tự quản lý một cấu trúc dữ liệu ánh xạ từ địa chỉ nguồn sang thông tin người chơi — thường là std::unordered_map với khóa là một dạng "chuẩn hóa" của sockaddr_in (bản thân sockaddr_in không có sẵn operator==/hàm băm để dùng trực tiếp làm khóa).

C++ — khoa dia chi va bang anh xa dia chi -> nguoi choi
#include <unordered_map>
#include <cstdint>

// Chuan hoa (IP, port) thanh 1 khoa 64-bit de dung lam key cho unordered_map,
// tranh phai tu viet ham bang/so sanh rieng cho struct sockaddr_in
struct AddrKey {
    uint32_t ip;    // dang network byte order, lay tu sin_addr.s_addr
    uint16_t port;  // dang network byte order, lay tu sin_port

    bool operator==(const AddrKey& other) const {
        return ip == other.ip && port == other.port;
    }
};

struct AddrKeyHash {
    size_t operator()(const AddrKey& k) const {
        // Ghep ip (32 bit) va port (16 bit) thanh 1 gia tri bam duy nhat
        return (static_cast<size_t>(k.ip) << 16) ^ k.port;
    }
};

struct PlayerInfo {
    int playerId;
    float x, y;
    double lastReceivedTime;   // dung o chuong 12 cho timeout
};

AddrKey MakeAddrKey(const sockaddr_in& addr) {
    return AddrKey{ addr.sin_addr.s_addr, addr.sin_port };
}

std::unordered_map<AddrKey, PlayerInfo, AddrKeyHash> g_players;
int g_nextPlayerId = 1;

// Goi moi khi nhan duoc 1 goi tin, sau khi da giai ma header (chuong 10)
PlayerInfo& GetOrCreatePlayer(const sockaddr_in& fromAddr) {
    AddrKey key = MakeAddrKey(fromAddr);
    auto it = g_players.find(key);
    if (it != g_players.end()) {
        return it->second;
    }
    // Chua tung thay dia chi nay - day la client MOI, khoi tao thong tin
    PlayerInfo newPlayer{};
    newPlayer.playerId = g_nextPlayerId++;
    newPlayer.x = 0.0f;
    newPlayer.y = 0.0f;
    printf("Client moi tham gia, gan player id = %d\n", newPlayer.playerId);
    auto result = g_players.emplace(key, newPlayer);
    return result.first->second;
}
Ghi chú: Đây chính là kỹ thuật nền tảng mà mọi middleware ở Phần IV-VIII (Photon, Netcode for GameObjects, FishNet) đều dùng bên trong lớp transport UDP của chúng — chỉ khác là chúng đóng gói sẵn thành các API bậc cao (ví dụ khái niệm "connection" hay "client id") để lập trình viên không phải tự quản lý bảng ánh xạ địa chỉ này bằng tay.
Cạm bẫy NAT re-binding: Một số NAT/router có thể đổi cổng nguồn công cộng của cùng một client giữa các gói tin (hiếm nhưng có thể xảy ra, đặc biệt với NAT loại "symmetric") — khi đó server sẽ nhầm tưởng đây là một client hoàn toàn mới vì cặp (IP, port) đã thay đổi. Các middleware thực tế giải quyết vấn đề này bằng cách gắn thêm một session ID/token ở tầng ứng dụng (bên trong payload, không dựa hoàn toàn vào địa chỉ mạng) — kỹ thuật này sẽ được nhắc lại khi bàn về thiết kế packet header ở chương 10.

4. Cấu trúc Game Loop kết hợp Non-blocking Socket

Với socket đã ở chế độ non-blocking, cấu trúc chuẩn của một game loop server (và tương tự cho client) trở thành:

Pseudocode — cau truc game loop chuan
while (running) {
    double frameStart = GetTime();

    ProcessAllPendingPackets();   // doc HET moi goi dang cho, non-blocking
    StepSimulation(fixedDeltaTime);
    SendUpdatesToClients();

    SleepUntilNextTick(frameStart, tickInterval);
}

Tại sao phải đọc HẾT mọi gói đang chờ, không chỉ 1 gói mỗi vòng lặp

Một sai lầm tinh vi là chỉ gọi recvfrom() đúng một lần mỗi vòng lặp, xử lý đúng một gói tin rồi đi tiếp sang bước simulation. Vấn đề: giữa hai lần tick liên tiếp của server (ví dụ cách nhau 50ms với tick rate 20Hz), nhiều gói tin có thể dồn tới cùng lúc từ nhiều client khác nhau — hệ điều hành xếp hàng (buffer) chúng trong một bộ đệm nhận (receive buffer) có kích thước giới hạn cho socket đó. Nếu mỗi tick chỉ "rút" đúng một gói ra khỏi bộ đệm trong khi tốc độ gói tin đến nhanh hơn tốc độ rút, bộ đệm sẽ dần đầy lên và tràn (overflow) — hệ điều hành buộc phải âm thầm loại bỏ (drop) các gói tin mới đến, gây mất dữ liệu game hoàn toàn không cần thiết dù bản thân mạng không hề có vấn đề gì.

Giải pháp: mỗi tick, gọi recvfrom() lặp đi lặp lại trong một vòng while cho tới khi nó trả về lỗi EWOULDBLOCK/EAGAIN — nghĩa là bộ đệm nhận đã thực sự rỗng, mọi gói tin đang chờ đã được "rút" hết ra và đưa vào xử lý.

C++ — doc het moi goi dang cho trong 1 lan tick
constexpr int MAX_PACKET_SIZE = 1200;  // duoi nguong phan manh MTU thong thuong

void ProcessAllPendingPackets(socket_t udpSocket) {
    char buffer[MAX_PACKET_SIZE];
    sockaddr_in fromAddr;

    for (;;) {
#ifdef _WIN32
        int fromLen = sizeof(fromAddr);
#else
        socklen_t fromLen = sizeof(fromAddr);
#endif
        memset(&fromAddr, 0, sizeof(fromAddr));

        int bytesReceived = recvfrom(udpSocket, buffer, sizeof(buffer), 0,
                                      (sockaddr*)&fromAddr, &fromLen);

        if (bytesReceived > 0) {
            // Co du lieu that - dua vao hang doi/xu ly ngay (giai ma header o chuong 10)
            HandleIncomingPacket(buffer, bytesReceived, fromAddr);
            continue;  // lap lai ngay, co the con goi khac dang cho
        }

        // bytesReceived <= 0: kiem tra co phai "chua co gi de doc" khong
#ifdef _WIN32
        int err = WSAGetLastError();
        if (err == WSAEWOULDBLOCK) {
            break;  // het goi dang cho that su, thoat vong lap
        }
        fprintf(stderr, "recvfrom() loi that: %d\n", err);
        break;
#else
        if (errno == EWOULDBLOCK || errno == EAGAIN) {
            break;  // het goi dang cho that su, thoat vong lap
        }
        fprintf(stderr, "recvfrom() loi that: %s\n", strerror(errno));
        break;
#endif
    }
}

5. Ví dụ đầy đủ: khởi tạo UDP Socket Non-blocking trên cả hai nền tảng

Ví dụ dưới đây ghép toàn bộ kiến thức của chương: tạo socket UDP, bind() vào một cổng cố định, chuyển sang non-blocking, rồi minh họa một khung game loop tối giản gọi ProcessAllPendingPackets() mỗi tick.

C++ — khoi tao UDP socket non-blocking va vong lap chinh
#ifdef _WIN32
  #include <winsock2.h>
  #include <ws2tcpip.h>
  #pragma comment(lib, "Ws2_32.lib")
  using socket_t = SOCKET;
  constexpr socket_t INVALID_SOCK = INVALID_SOCKET;
#else
  #include <sys/socket.h>
  #include <netinet/in.h>
  #include <arpa/inet.h>
  #include <unistd.h>
  #include <fcntl.h>
  #include <cerrno>
  using socket_t = int;
  constexpr socket_t INVALID_SOCK = -1;
#endif
#include <cstdio>
#include <cstring>
#include <chrono>
#include <thread>

bool SetSocketNonBlocking(socket_t sock) {
#ifdef _WIN32
    u_long mode = 1;
    return ioctlsocket(sock, FIONBIO, &mode) == 0;
#else
    int flags = fcntl(sock, F_GETFL, 0);
    if (flags == -1) return false;
    return fcntl(sock, F_SETFL, flags | O_NONBLOCK) != -1;
#endif
}

socket_t CreateGameServerSocket(uint16_t port) {
#ifdef _WIN32
    WSADATA wsaData;
    WSAStartup(MAKEWORD(2, 2), &wsaData);
#endif
    socket_t sock = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
    if (sock == INVALID_SOCK) {
        fprintf(stderr, "socket() that bai\n");
        return INVALID_SOCK;
    }

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(port);
    addr.sin_addr.s_addr = htonl(INADDR_ANY);

    if (bind(sock, (sockaddr*)&addr, sizeof(addr)) != 0) {
        fprintf(stderr, "bind() that bai tren cong %d\n", port);
        return INVALID_SOCK;
    }

    if (!SetSocketNonBlocking(sock)) {
        fprintf(stderr, "Khong the chuyen sang non-blocking\n");
        return INVALID_SOCK;
    }

    printf("Game server UDP dang lang nghe tren cong %d (non-blocking)\n", port);
    return sock;
}

double GetTimeSeconds() {
    using namespace std::chrono;
    return duration<double>(steady_clock::now().time_since_epoch()).count();
}

void HandleIncomingPacket(const char* data, int len, const sockaddr_in& from) {
    // Giai ma header + payload se hoc o chuong 10 - o day chi in log minh hoa
    char ip[INET_ADDRSTRLEN];
    inet_ntop(AF_INET, &from.sin_addr, ip, sizeof(ip));
    printf("Nhan %d byte tu %s:%d\n", len, ip, ntohs(from.sin_port));
}

void ProcessAllPendingPackets(socket_t udpSocket) {
    char buffer[1200];
    for (;;) {
        sockaddr_in fromAddr{};
#ifdef _WIN32
        int fromLen = sizeof(fromAddr);
#else
        socklen_t fromLen = sizeof(fromAddr);
#endif
        int n = recvfrom(udpSocket, buffer, sizeof(buffer), 0, (sockaddr*)&fromAddr, &fromLen);
        if (n > 0) {
            HandleIncomingPacket(buffer, n, fromAddr);
            continue;
        }
#ifdef _WIN32
        if (WSAGetLastError() == WSAEWOULDBLOCK) break;
#else
        if (errno == EWOULDBLOCK || errno == EAGAIN) break;
#endif
        break;
    }
}

int main() {
    socket_t serverSocket = CreateGameServerSocket(9000);
    if (serverSocket == INVALID_SOCK) return 1;

    const double tickInterval = 1.0 / 20.0;  // 20 tick/giay
    bool running = true;

    while (running) {
        double frameStart = GetTimeSeconds();

        ProcessAllPendingPackets(serverSocket);
        // StepSimulation(tickInterval);       // se trien khai day du o chuong 14
        // SendUpdatesToClients();             // se trien khai day du o chuong 14

        double elapsed = GetTimeSeconds() - frameStart;
        double sleepTime = tickInterval - elapsed;
        if (sleepTime > 0) {
            std::this_thread::sleep_for(std::chrono::duration<double>(sleepTime));
        }
    }

#ifdef _WIN32
    closesocket(serverSocket);
    WSACleanup();
#else
    close(serverSocket);
#endif
    return 0;
}

Tổng kết chương

Ba điểm cốt lõi cần mang theo sang các chương tiếp: (1) mọi socket tham gia game loop realtime phải là non-blocking, và EWOULDBLOCK/EAGAIN là tín hiệu bình thường chứ không phải lỗi; (2) một socket UDP server duy nhất phục vụ mọi client thông qua việc so sánh địa chỉ nguồn (IP, port) trả về từ recvfrom(), đòi hỏi tự quản lý một bảng ánh xạ; (3) game loop phải rút cạn toàn bộ gói tin đang chờ trong bộ đệm hệ điều hành ở mỗi tick trước khi bước sang tính simulation. Chương 10 sẽ dùng đúng nền tảng non-blocking này để thiết kế cấu trúc packet nhị phân — thứ thực sự nằm bên trong buffer mà recvfrom() vừa đọc được.
