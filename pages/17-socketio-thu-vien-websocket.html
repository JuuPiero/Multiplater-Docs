PHẦN III · WEBSOCKET & MULTIPLAYER TRÌNH DUYỆT

Socket.IO & Thư viện WebSocket phổ biến

Chương 15-16 đã trình bày WebSocket "trần" — đúng đặc tả RFC 6455, dùng thẳng API WebSocket có sẵn của trình duyệt. Trong thực tế phát triển, đặc biệt cho các use case lobby/chat/matchmaking đã nêu ở chương 16, phần lớn dự án không dùng WebSocket API gốc trực tiếp mà thông qua một thư viện bao bọc (wrapper) tiện lợi hơn. Phổ biến nhất trong số đó là Socket.IO. Chương này giải thích Socket.IO thực sự là gì, những tiện ích nó bổ sung, và khi nào nên chọn nó thay vì WebSocket thuần.

1. Socket.IO là gì — và không phải là gì

Hiểu đúng ngay từ đầu: Socket.IO KHÔNG PHẢI một giao thức chuẩn độc lập giống WebSocket (RFC 6455). Nó là một thư viện (có cả phần server lẫn phần client) được xây dựng trên nền WebSocket, bổ sung thêm một tầng logic riêng của mình bên trên. Hai đầu client và server đều phải cùng dùng thư viện Socket.IO — một client Socket.IO không thể kết nối thẳng tới một server WebSocket thuần (và ngược lại) vì giao thức tầng ứng dụng bên trên đã khác nhau, dù cả hai cùng dùng chung nền tảng WebSocket bên dưới.

2. Các tiện ích chính mà Socket.IO bổ sung

Tự động Fallback (dự phòng) sang HTTP Long-Polling

Đây là tính năng đặc trưng nhất của Socket.IO. Trong một số môi trường doanh nghiệp hiếm gặp, firewall hoặc proxy trung gian có thể chặn hoàn toàn giao thức WebSocket (dù việc này ngày càng hiếm khi WebSocket đã phổ biến rộng rãi). Khi Socket.IO phát hiện không thể thiết lập kết nối WebSocket, nó tự động chuyển sang dùng kỹ thuật HTTP Long-Polling (đã giới thiệu ở chương 15) để vẫn duy trì được giao tiếp, đánh đổi hiệu năng (độ trễ cao hơn, overhead lớn hơn) lấy độ tin cậy kết nối trong mọi hoàn cảnh mạng.

Auto-Reconnect (tự động kết nối lại)

Khi kết nối bị ngắt tạm thời (ví dụ người chơi di chuyển giữa các điểm phát Wi-Fi, mất mạng vài giây), Socket.IO tự động thử kết nối lại theo một chiến lược có thể cấu hình (thời gian chờ giữa các lần thử, số lần thử tối đa), mà không cần lập trình viên tự viết logic theo dõi trạng thái kết nối và gọi lại new WebSocket(...) thủ công như khi dùng API gốc.

Room & Namespace

Room (phòng) là khái niệm nhóm các client kết nối lại với nhau theo một định danh tuỳ ý (ví dụ "lobby-01", "match-4523"), giúp việc gửi broadcast (phát) một thông điệp tới đúng một nhóm người chơi cụ thể trở nên đơn giản, thay vì phải gửi tới toàn bộ client đang kết nối rồi tự lọc thủ công ở phía ứng dụng. Namespace (không gian tên) là một mức phân chia rộng hơn, thường dùng để tách các luồng giao tiếp có mục đích khác nhau trên cùng một server (ví dụ namespace /chat và namespace /game dùng chung một kết nối vật lý nhưng logic xử lý độc lập). Khái niệm Room ở đây có tinh thần rất giống khái niệm Room sẽ gặp lại ở Photon PUN (chương 21) — cùng là "nhóm người chơi cùng nhận sự kiện của nhau", dù cơ chế triển khai bên dưới của hai hệ thống khác nhau hoàn toàn.

Event-based API

Thay vì phải tự phân tích (parse) từng frame thô hay tự định nghĩa cấu trúc message thủ công, Socket.IO cung cấp phong cách lập trình theo sự kiện có tên (named events): socket.on("eventName", callback) để đăng ký lắng nghe, và socket.emit("eventName", data) để phát sự kiện kèm dữ liệu. Phong cách này rất gần gũi với hệ thống sự kiện (event system) quen thuộc vốn có sẵn trong hầu hết engine game (ví dụ delegate/event trong C#, hoặc hệ thống Observer pattern phổ biến trong lập trình game nói chung).

Acknowledgement (xác nhận đã xử lý)

Khác với WebSocket thuần (nơi send() không có cách nào biết phía kia đã xử lý xong dữ liệu chưa), Socket.IO hỗ trợ sẵn cơ chế acknowledgement: bên gọi emit() có thể truyền thêm một callback ở tham số cuối, callback này sẽ được gọi lại khi bên nhận xác nhận đã xử lý xong sự kiện — tương tự mô hình request-response nhưng vẫn nằm trên nền một kết nối WebSocket bền. Hữu ích cho các thao tác cần biết chắc chắn "server đã nhận và xử lý xong" trước khi client cập nhật giao diện, ví dụ xác nhận đã tham gia phòng thành công.

Middleware xác thực (Authentication Middleware)

Socket.IO cho phép đăng ký các hàm middleware chạy trước khi một kết nối được chấp nhận chính thức — thường dùng để kiểm tra token đăng nhập (ví dụ JWT — JSON Web Token, một định dạng token phổ biến để xác thực người dùng) gửi kèm trong lúc handshake, từ chối kết nối ngay từ đầu nếu token không hợp lệ, thay vì phải tự kiểm tra thủ công ở mỗi sự kiện sau khi đã kết nối.

3. Ví dụ code: server và client Socket.IO tối giản

JavaScript (Node.js) — server Socket.IO voi Room
const { Server } = require("socket.io");
const io = new Server(3000);

io.on("connection", (socket) => {
    console.log("Client moi ket noi:", socket.id);

    socket.on("joinLobby", (lobbyId) => {
        socket.join(lobbyId);              // tham gia mot "Room" theo ten lobbyId
        io.to(lobbyId).emit("playerJoined", { id: socket.id });
    });

    socket.on("chatMessage", (data) => {
        // Chi phat lai cho cac client trong CUNG mot Room, khong phai toan bo server
        io.to(data.lobbyId).emit("chatMessage", data);
    });

    socket.on("disconnect", () => {
        console.log("Client ngat ket noi:", socket.id);
    });
});
JavaScript — client Socket.IO tuong ung
// Can nhung the <script src=".../socket.io.js"> hoac import tu package "socket.io-client"
const socket = io("wss://game.example.com");

socket.emit("joinLobby", "lobby-01");

socket.on("playerJoined", (data) => {
    console.log("Nguoi choi moi vao lobby:", data.id);
});

socket.on("chatMessage", (data) => {
    console.log(`[${data.sender}]: ${data.text}`);
});

// Gui tin nhan chat
socket.emit("chatMessage", { lobbyId: "lobby-01", sender: "Player1", text: "Xin chao!" });
JavaScript — emit voi Acknowledgement callback
// Client goi emit kem callback o tham so cuoi
socket.emit("joinLobby", "lobby-01", (response) => {
    if (response.ok) {
        console.log("Server da xac nhan tham gia lobby thanh cong");
    } else {
        console.error("Tham gia that bai:", response.error);
    }
});

// Phia server, nhan them tham so "callback" o cuoi handler de goi nguoc lai
io.on("connection", (socket) => {
    socket.on("joinLobby", (lobbyId, callback) => {
        socket.join(lobbyId);
        callback({ ok: true });   // "ack" bao cho client biet da xu ly xong
    });
});

3b. Scaling Socket.IO qua nhiều server: vấn đề Room xuyên máy chủ

Lý thuyết Mặc định, khái niệm Room của Socket.IO chỉ tồn tại trong bộ nhớ của một tiến trình server duy nhất — nếu triển khai nhiều instance server song song để chịu tải (giống vấn đề Sticky Session đã nhắc ở chương 16), hai client cùng ở một Room logic nhưng kết nối tới hai server vật lý khác nhau sẽ không thể nhận broadcast của nhau nếu không có thêm cấu hình. Giải pháp phổ biến là dùng một Adapter trung gian (ví dụ Redis Adapter — dựa trên Redis, một kho dữ liệu in-memory thường dùng làm message broker) để đồng bộ sự kiện Room giữa các instance server. Đây là kiến trúc điển hình khi lobby/chat của game cần mở rộng ra nhiều server, chủ đề sẽ được bàn sâu hơn ở chương 50.

Thư viện / APIĐặc điểmPhù hợp khi nào
ws (Node.js)Thư viện WebSocket thuần cho Node.js phía server, nhẹ, không có fallback hay Room tích hợp sẵn — implement gần sát đặc tả RFC 6455 nhất trong các lựa chọn phổ biến.Khi cần kiểm soát chi tiết hành vi giao thức, tối ưu hiệu năng tối đa, hoặc tự xây dựng framework riêng bên trên.

5. Bảng quyết định: Socket.IO hay raw WebSocket?

Gợi ý thực dụng: Với các use case lobby/chat/matchmaking đã nêu ở chương 16 — nơi tốc độ phát triển và độ tin cậy kết nối thường quan trọng hơn việc tối ưu từng byte — Socket.IO thường là lựa chọn hợp lý. Ngược lại, nếu team đã tự kiểm soát toàn bộ hạ tầng triển khai (biết chắc không có proxy chặn WebSocket) và muốn tối ưu băng thông/độ trễ tối đa, raw WebSocket hoặc thư viện nhẹ như ws sẽ phù hợp hơn.
