PHẦN IX · SO SÁNH, KIẾN TRÚC NÂNG CAO & PHỤ LỤC

Hosting, Scaling & Matchmaking Cloud

Chọn đúng kiến trúc mạng (Phần II–VIII, cộng thêm Lockstep/Rollback ở chương 49) mới chỉ là một nửa bài toán — nửa còn lại là vận hành nó trong môi trường thật: server chạy ở đâu, ai lo việc bật thêm server khi lượng người chơi tăng đột biến, và người chơi được ghép trận với nhau như thế nào. Chương này giới thiệu các dịch vụ cloud chuyên trách cho bài toán đó — PlayFab, AWS GameLift, Unity Game Server Hosting, và hạ tầng Photon Cloud — cùng hai công nghệ nền tảng đứng sau phần lớn các dịch vụ này: Docker và Kubernetes, và khái niệm matchmaking nâng cao vượt xa việc lọc phòng đơn giản đã học ở chương 24.

1. Backend-as-a-Service (BaaS) cho Game — PlayFab

PlayFab

Microsoft PlayFab là một nền tảng "Backend-as-a-Service" (BaaS — dịch vụ hạ tầng phụ trợ đóng gói sẵn, không cần tự dựng server riêng cho từng chức năng) dành riêng cho game. Thay vì tự viết server để lưu điểm số, xếp hạng người chơi, hay ghép trận, PlayFab cung cấp sẵn các dịch vụ này dưới dạng API gọi trực tiếp từ game client hoặc server: Matchmaking (ghép trận), Leaderboard (bảng xếp hạng), và lưu trữ dữ liệu người chơi (player data, inventory, thống kê). PlayFab tích hợp SDK chính thức cho cả Unity lẫn Unreal Engine, cũng như C++/C# thuần cho các dự án tự viết engine, nên có thể dùng chung một backend cho nhiều dự án khác engine nhau trong cùng studio.

2. Hosting & Auto-scaling Dedicated Server — AWS GameLift

AWS GameLift

Amazon GameLift là dịch vụ của AWS (Amazon Web Services) chuyên trách việc host và tự động scale (auto-scaling) các Dedicated Server theo đúng nhu cầu thực tế tại từng thời điểm — khi số lượng người chơi đang chờ ghép trận tăng cao, GameLift tự động khởi động thêm instance server mới; khi lượng người chơi giảm, các instance thừa được tắt bớt để tiết kiệm chi phí. Đây chính là câu trả lời trực tiếp cho vấn đề chi phí Dedicated Server đã nhắc tới ở chương 46: thay vì phải tự thuê và trả tiền cho một số lượng server cố định (dù giờ cao điểm hay giờ vắng khách), chi phí co giãn theo đúng tải thực tế. GameLift hỗ trợ tốt các server build từ Unreal Engine lẫn server C++ tự viết đóng gói thành file thực thi (executable) chuẩn.

Thuật ngữ riêng của GameLift: Fleet — một nhóm instance server chạy cùng một build cụ thể, đơn vị cơ bản để cấu hình auto-scaling; Game Session — một phiên chơi cụ thể (tương đương khái niệm Room ở Photon) chạy trên một trong các instance của Fleet; Player Session — một chỗ ngồi cụ thể trong Game Session, được cấp cho từng người chơi khi họ được ghép vào trận. Ba khái niệm này lồng vào nhau theo đúng thứ tự Fleet → Game Session → Player Session.

3. Dịch vụ Hosting chính thức của Unity — Unity Game Server Hosting

Unity Game Server Hosting (Multiplay)

Unity Game Server Hosting (thường được biết tới với tên cũ Multiplay) là dịch vụ hosting chính thức của Unity Technologies, tích hợp trực tiếp và liền mạch với Netcode for GameObjects (NGO — chương 32–37): build Dedicated Server headless của dự án NGO có thể được deploy thẳng lên hạ tầng của Unity, kèm theo cơ chế fleet management (quản lý một "hạm đội" nhiều instance server) và auto-scaling tương tự triết lý của GameLift, nhưng được thiết kế để cấu hình thuận tiện nhất trong hệ sinh thái Unity Gaming Services (cùng nhóm với Unity Relay/Lobby đã học ở chương 36).

4. Photon Cloud cho cả PUN 2 lẫn Fusion Dedicated Server

Photon Cloud

Chương 20 đã giới thiệu Photon Cloud như hạ tầng Relay đứng sau PUN 2 — nơi các client kết nối vào để được ghép Room mà không cần ai tự host server. Ở phía Fusion 2 (Phần V), Photon còn cung cấp thêm một dịch vụ riêng biệt cho phép host Dedicated Server thật của Fusion ngay trên hạ tầng Photon, thay vì bắt buộc phải tự thuê máy chủ ở nơi khác — kết hợp được lợi thế "không cần tự quản lý hạ tầng" của PUN 2 với mô hình Server thật đúng nghĩa (Authoritative Server) mà Fusion hỗ trợ.

5. Đóng gói bằng Docker

Lý thuyết Docker là công cụ đóng gói một ứng dụng — ví dụ file thực thi Dedicated Server của Unreal (chương 46) hay một game server C++ tự viết bằng Socket thô (Phần II) — cùng toàn bộ thư viện và cấu hình môi trường nó cần, thành một đơn vị độc lập gọi là container. Container chạy giống hệt nhau bất kể máy chủ vật lý hay hệ điều hành nền bên dưới là gì (miễn có Docker runtime), giải quyết triệt để vấn đề kinh điển "chạy được trên máy tôi nhưng không chạy được trên máy production" khi triển khai server thực tế.

Dockerfile (minh hoạ) — đóng gói một Dedicated Server Linux tự viết bằng C++
# Dockerfile toi gian dong goi mot game server build san
FROM ubuntu:22.04

# Cai cac thu vien runtime can thiet (vi du libc, libstdc++...)
RUN apt-get update && apt-get install -y libstdc++6 && rm -rf /var/lib/apt/lists/*

# Copy file thuc thi server da build san vao image
COPY GameServer /app/GameServer
WORKDIR /app

# Mo cong UDP ma server lang nghe (vi du 7777)
EXPOSE 7777/udp

# Lenh chay khi container khoi dong
CMD ["./GameServer", "--port=7777"]

6. Điều phối quy mô lớn bằng Kubernetes

Lý thuyết Khi số lượng container Dedicated Server cần chạy lên tới hàng chục, hàng trăm, việc khởi động/tắt/theo dõi sức khoẻ (health check) từng container thủ công không còn khả thi. Kubernetes (thường viết tắt K8s) là hệ thống điều phối (orchestration) container tự động: tự động khởi động thêm container khi cần scale lên, tự động thay thế container bị crash, và phân phối tải giữa nhiều máy chủ vật lý/máy ảo trong một "cluster". Đây là công nghệ nền phổ biến đứng sau việc scale Dedicated Server ở quy mô lớn trong ngành công nghiệp game hiện đại — nhiều dịch vụ như GameLift hay Multiplay thực chất vận hành một lớp điều phối tương tự triết lý Kubernetes bên dưới lớp API thân thiện với lập trình viên game.

flowchart TD MM["Matchmaking Service"] -->|"Yeu cau: can 1 server moi cho tran dau"| K8S["Kubernetes Control Plane"] K8S -->|"Chon node con trong tai"| N1["Node vat ly / VM 1"] K8S -->|"Hoac"| N2["Node vat ly / VM 2"] N1 --> C1["Container: Dedicated Server - tran dau A"] N2 --> C2["Container: Dedicated Server - tran dau B"] K8S -.->|"Tu dong theo doi suc khoe, restart neu crash"| C1 K8S -.->|"Tu dong theo doi suc khoe, restart neu crash"| C2 K8S -->|"Het tran, giai phong container"| N1
Kubernetes (minh hoạ) — manifest tối giản mô tả một Deployment Dedicated Server
# deployment.yaml - dinh nghia mot "Deployment" chay 3 ban sao container Dedicated Server
apiVersion: apps/v1
kind: Deployment
metadata:
  name: game-server
spec:
  replicas: 3                     # so container Dedicated Server chay dong thoi
  selector:
    matchLabels:
      app: game-server
  template:
    metadata:
      labels:
        app: game-server
    spec:
      containers:
        - name: game-server
          image: myregistry/game-server:1.0.0   # image Docker da build tu Dockerfile
          ports:
            - containerPort: 7777
              protocol: UDP
          resources:
            requests:
              cpu: "500m"          # dam bao toi thieu nua loi CPU cho moi container
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"
Ghi chú: Đây chỉ là ví dụ khung sườn để hình dung cấu trúc khai báo — triển khai Dedicated Server thật trên Kubernetes trong thực tế thường cần thêm các thành phần chuyên biệt như GameServer custom resource của dự án mã nguồn mở Agones (một lớp xây trên Kubernetes dành riêng cho game server, quản lý vòng đời phiên chơi tốt hơn Deployment thông thường), nằm ngoài phạm vi chi tiết của tài liệu này.

6.1. Tối ưu chi phí: Spot Instance và cân nhắc Vendor Lock-in

Cả GameLift, Multiplay lẫn một cluster Kubernetes tự quản đều có thể tận dụng Spot Instance (máy ảo được thuê với giá rẻ hơn đáng kể so với giá thông thường, đổi lại nhà cung cấp có quyền thu hồi lại bất kỳ lúc nào khi cần công suất cho khách hàng trả giá đầy đủ) cho các Fleet Dedicated Server không quá nhạy cảm với việc bị ngắt đột ngột — kết hợp cùng chiến lược tự động di chuyển người chơi sang instance khác khi một Spot Instance bị thu hồi. Ở chiều ngược lại, cần cân nhắc vendor lock-in (bị phụ thuộc chặt vào một nhà cung cấp cụ thể): thiết kế server phụ thuộc quá sâu vào API riêng của một dịch vụ cloud (ví dụ gọi thẳng SDK GameLift trong logic gameplay lõi thay vì qua một lớp trừu tượng hoá riêng) khiến việc chuyển sang dịch vụ khác trong tương lai — nếu chi phí hoặc chính sách thay đổi bất lợi — trở nên tốn kém hơn nhiều so với khi đã tách lớp tích hợp cloud ra một module riêng biệt ngay từ đầu.

7. Matchmaking Service nâng cao

Chương 24 đã giới thiệu matchmaking ở mức đơn giản của PUN 2: lọc phòng theo Custom Properties (ví dụ chỉ tìm phòng đúng chế độ chơi, đúng bản đồ). Ở quy mô sản phẩm thương mại, matchmaking service thường cần thêm hai lớp logic nâng cao sau:

7.1. Skill-Based Matchmaking (SBMM)

Lý thuyết SBMM (Skill-Based Matchmaking — ghép trận theo trình độ) cố gắng ghép những người chơi có trình độ tương đương vào cùng một trận, thay vì ghép ngẫu nhiên hoàn toàn, nhằm tránh tình trạng người mới liên tục gặp người chơi kỳ cựu (trải nghiệm gây nản lòng cho cả hai phía). Các thuật toán phổ biến nhất trong ngành gồm Elo (hệ thống xếp hạng gốc từ cờ vua), Glicko/Glicko-2 (cải tiến của Elo, có thêm độ "tin cậy" của điểm số theo số trận đã chơi), và TrueSkill (do Microsoft Research phát triển, hỗ trợ tốt cho các trận đấu nhiều hơn 2 người/2 đội). Tài liệu này chỉ giới thiệu khái niệm để người đọc nhận diện được thuật ngữ khi gặp trong tài liệu của các dịch vụ matchmaking — không đi sâu vào công thức toán học cụ thể của từng thuật toán.

7.2. Region-based Matchmaking

Liên hệ trực tiếp với khái niệm độ trễ (Latency/RTT) đã học ở chương 2: ghép trận ưu tiên những người chơi ở cùng khu vực địa lý (region) — hoặc ít nhất có độ trễ mạng tới cùng một cụm server thấp tương đương nhau — để đảm bảo trải nghiệm công bằng và giảm độ trễ trung bình toàn trận, thay vì ghép hoàn toàn ngẫu nhiên bất kể vị trí địa lý khiến một số người chơi phải chịu RTT rất cao so với phần còn lại.

7.3. Toàn cảnh một luồng matchmaking hoàn chỉnh

Sơ đồ dưới đây ghép cả SBMM lẫn Region-based Matchmaking cùng bước cấp phát Fleet/Dedicated Server (mục 2, 3) thành một luồng thống nhất, để hình dung rõ thứ tự các quyết định được đưa ra từ lúc người chơi bấm "Tìm trận" tới lúc thực sự kết nối vào Dedicated Server:

Tổng kết chương

Việc có một Dedicated Server thật (Phần V, VI, VII, VIII) mới chỉ giải quyết được bài toán kiến trúc mạng — vận hành nó ở quy mô hàng nghìn trận đấu đồng thời, với chi phí hợp lý và khả năng ghép trận công bằng, là một bài toán vận hành (operations) hoàn toàn riêng biệt mà PlayFab, GameLift, Multiplay, Docker và Kubernetes được sinh ra để giải quyết. Chương tiếp theo quay trở lại tầng giao thức, đi sâu hơn vào các kỹ thuật tối ưu băng thông nâng cao — delta compression và quantization — vốn cũng góp phần trực tiếp làm giảm chi phí hosting đã bàn ở chương này, vì băng thông tiêu thụ mỗi client thường là một thành phần tính phí quan trọng của hầu hết các dịch vụ cloud vừa giới thiệu.
