PHẦN VIII · UNREAL ENGINE NETWORKING

Replication & RPC trong Unreal (Recap)

Chương 43 đã xác lập rằng Unreal có sẵn một hệ thống networking hoàn chỉnh. Chương này tóm tắt nhanh hai cơ chế cốt lõi vận hành hệ thống đó — Replication (Server → Client) và RPC (chủ yếu Client → Server, cùng các chiều thông báo khác) — chỉ đủ để nhận ra chúng khi đọc code Unreal, không đi sâu từng dòng như bộ tài liệu Unreal C++ đầy đủ (nơi trình bày chi tiết cả năm bước bắt buộc, các điều kiện Replicate có chọn lọc, và toàn bộ giới hạn thực tế của RPC). Trọng tâm thật sự của chương nằm ở bảng đối chiếu thuật ngữ ngay bên dưới — bảng quan trọng nhất của toàn bộ Phần VIII — ghép mỗi khái niệm Unreal với đúng khái niệm tương đương ở cả bốn middleware Unity đã học.

Replication — recap: Server tự động "sao chép" giá trị xuống Client

Bản chất không đổi so với các cơ chế đồng bộ trạng thái đã học ở Phần IV–VII: lập trình viên chỉ sửa giá trị biến ngay trên Server (trong khối có HasAuthority()), còn việc đóng gói, gửi qua mạng, và gán lại đúng giá trị trên mọi Client là việc của engine. Bốn bước bắt buộc, tóm gọn:

#Bước bắt buộc
1Actor bật bReplicates = true; trong constructor
2Đánh dấu biến bằng UPROPERTY(Replicated) hoặc UPROPERTY(ReplicatedUsing=OnRep_TenHam)
3Override GetLifetimeReplicatedProps()
4Gọi DOREPLIFETIME(LopActor, TenBien); cho từng biến bên trong hàm ở bước 3
Unreal C++ Khai báo Health Replicated kèm RepNotify — recap cú pháp
// MyCharacter.h
UPROPERTY(ReplicatedUsing = OnRep_Health)
float Health;

UFUNCTION()
void OnRep_Health();

// MyCharacter.cpp
void AMyCharacter::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);
    DOREPLIFETIME(AMyCharacter, Health); // thieu dong nay: Health KHONG BAO GIO dong bo
}

void AMyCharacter::ApplyDamage(float DamageAmount)
{
    if (!HasAuthority()) return;      // chi Server duoc phep sua gia tri that
    Health = FMath::Clamp(Health - DamageAmount, 0.0f, MaxHealth);
}

void AMyCharacter::OnRep_Health()
{
    // CHI duoc engine tu dong goi tren Client, khong bao gio tu chay tren Server
    UpdateHealthUI();
}
Đọc sâu hơn: Năm bước đầy đủ, các điều kiện lọc DOREPLIFETIME_CONDITION (ví dụ COND_OwnerOnly để chỉ gửi cho đúng Owner — tiết kiệm băng thông giống tinh thần Interest Management đã học ở chương 7), và bảng các kiểu dữ liệu Replicate được, được trình bày đầy đủ trong bộ tài liệu Unreal Engine C++ riêng (phần Networking & Multiplayer, chương về Replication).

RPC — recap: ba loại, Reliable/Unreliable, quy ước _Implementation

RPC (Remote Procedure Call) là con đường duy nhất để một máy chủ động yêu cầu một máy khác thực thi logic — đúng vai trò mà mọi middleware Unity đã học cũng phải giải quyết theo cách riêng của mình. Ba loại UFUNCTION specifier của Unreal, tóm tắt:

LoạiGọi từ đâu → thực thi ở đâuDùng khi nào
ServerClient (chỉ Owner) → ServerClient yêu cầu Server thực hiện hành động cần kiểm tra hợp lệ — "tôi muốn bắn"
ClientServer → đúng một Client cụ thể (Owner)Server báo riêng cho một người chơi — "bạn vừa lên cấp"
NetMulticastServer → Server + mọi ClientHiệu ứng/sự kiện mọi người đều cần thấy — hiệu ứng nổ, âm thanh súng
Unreal C++ Khai báo RPC — recap quy ước bắt buộc
UFUNCTION(Server, Reliable, WithValidation)
void ServerFire();

// Logic THAT su o day, hau to _Implementation la BAT BUOC
void AMyCharacter::ServerFire_Implementation()
{
    // ...
}

// Goi noi khac luon dung TEN GOC, KHONG goi thang _Implementation
ServerFire();

Reliable đảm bảo gói tin luôn tới nơi (gửi lại nếu thất lạc, tốn băng thông hơn) — dùng cho hành động quan trọng không được phép mất. Unreliable không đảm bảo tới nơi nhưng nhẹ hơn — dùng cho dữ liệu cập nhật liên tục, mất một lần không sao vì lần sau ghi đè ngay.

Vì sao PUN thiếu nhiều "ô" trong bảng: Không phải PUN yếu hơn — mà vì PUN được thiết kế đơn giản hóa tối đa cho một mô hình relay không có Server thật (chương 20), nên không cần (và không có) các khái niệm đòi hỏi phân biệt "ai gửi, ai nhận, ai có quyền" một cách chặt chẽ như bốn hệ thống có Server thật còn lại. Đây chính là lý do PUN dễ học nhất nhưng cũng hạn chế nhất về khả năng chống gian lận (đã phân tích ở chương 20–25).

Ví dụ đối chiếu trực tiếp: cùng một hành động "bắn súng"

Để thấy bảng trên "sống" trong code thực tế, đây là cùng một luồng — Client bấm bắn, Server xử lý, mọi người thấy hiệu ứng — viết bằng đúng cú pháp của Unreal:

sequenceDiagram participant C as Client (nguoi choi bam ban) participant S as Server (co Authority) participant Others as Cac Client khac C->>S: ServerFire() - UFUNCTION(Server, Reliable) Note over S: Kiem tra con dan khong (logic that, chi chay tren Server) S-->>C: NetMulticastPlayFireEffect() - UFUNCTION(NetMulticast) S-->>Others: NetMulticastPlayFireEffect() - toi moi Client

So với sơ đồ tương đương ở chương 34 của bộ tài liệu Fusion (RPC loại RpcSources.InputAuthority → RpcTargets.StateAuthority, rồi State Authority multicast lại), hoặc ở chương 40 của bộ tài liệu FishNet ([ServerRpc] rồi [ObserversRpc]) — cấu trúc luồng dữ liệu giống hệt nhau, chỉ khác tên hàm và specifier.

Unreal C++ Luồng bắn súng hoàn chỉnh — recap cú pháp ba loại RPC
UCLASS()
class MYGAME_API UWeaponComponent : public UActorComponent
{
    GENERATED_BODY()
public:
    void RequestFire() { ServerFire(); } // Client goi ham nay tu Input

protected:
    UPROPERTY(EditDefaultsOnly) int32 AmmoCount = 10;

    UFUNCTION(Server, Reliable, WithValidation)
    void ServerFire();
    void ServerFire_Implementation();
    bool ServerFire_Validate() { return true; }

    UFUNCTION(NetMulticast, Unreliable)
    void NetMulticastPlayFireEffect();
    void NetMulticastPlayFireEffect_Implementation();

    UFUNCTION(Client, Reliable)
    void ClientNotifyOutOfAmmo();
    void ClientNotifyOutOfAmmo_Implementation();
};

void UWeaponComponent::ServerFire_Implementation()
{
    // Chay THAT su tren Server, du duoc goi tu Client nao
    if (AmmoCount <= 0) { ClientNotifyOutOfAmmo(); return; }
    AmmoCount--;
    NetMulticastPlayFireEffect(); // moi nguoi deu thay hieu ung
}

Kết luận chương

Toàn bộ năm hệ thống — Unreal, PUN, Fusion, NGO, FishNet — đều giải quyết chính xác cùng những bài toán: đồng bộ trạng thái một chiều Server → Client, gọi hành động Client → Server, thông báo Server → một/mọi Client, và phân định rõ "ai có quyền quyết định" khỏi "ai sở hữu". Chỉ có tên gọi và cú pháp cụ thể là khác nhau. Đây là lý do quan trọng nhất khiến việc học sâu bất kỳ một hệ thống nào trong số này — kể cả hệ thống built-in của Unreal — đều giúp học các hệ thống còn lại nhanh hơn đáng kể, vì bản chất khái niệm đằng sau luôn giống nhau. Chương 45 sẽ dùng chính nền tảng này để đưa ra một bảng quyết định thực tế: khi nào nên dùng built-in, khi nào cần cân nhắc middleware, tùy theo engine đang chọn cho dự án.
