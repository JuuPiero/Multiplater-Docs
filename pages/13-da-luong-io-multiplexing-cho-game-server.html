PHẦN II · LẬP TRÌNH SOCKET CHO GAME

Đa luồng & I/O Multiplexing cho Game Server

Bộ tài liệu Mạng máy tính đã trình bày đầy đủ select()/poll(), epoll() (Linux) và IOCP (Windows) như những cơ chế I/O multiplexing tổng quát. Chương này không lặp lại cơ chế đó, mà đặt câu hỏi kiến trúc cụ thể hơn: một game server thực tế nên tổ chức luồng (thread) như thế nào? Câu trả lời, có phần bất ngờ với nhiều người mới: kiến trúc phổ biến và an toàn nhất tách I/O mạng khỏi simulation logic bằng hàng đợi, nhưng bản thân simulation logic gần như luôn nên chạy đơn luồng — đúng như cách Unity và Unreal Engine đã chọn.

1. Kiến trúc tách biệt: Luồng Network I/O và Luồng Simulation

Một kiến trúc phổ biến cho game server quy mô vừa và lớn tách riêng hai mối quan tâm hoàn toàn khác nhau về bản chất:

  • Luồng (hoặc vài luồng) Network I/O: chuyên trách nhận/gửi gói tin qua socket — dùng non-blocking (chương 9) kết hợp epoll/IOCP để xử lý hiệu quả cùng lúc nhiều kết nối/nhiều client mà không lãng phí CPU chờ đợi.
  • Luồng Simulation/Game Logic: chuyên chạy vòng lặp tick cố định (chương 4, Phần I) — tính vật lý, va chạm, AI, cập nhật trạng thái thế giới game.

Hai luồng này không gọi hàm trực tiếp lẫn nhau và không chia sẻ trực tiếp cấu trúc dữ liệu phức tạp — chúng giao tiếp thông qua một cặp hàng đợi an toàn luồng (thread-safe queue):

Luồng Network I/O, sau khi nhận và giải mã một gói tin (dùng packet header từ chương 10), đẩy gói tin đã xử lý vào hàng đợi Input để luồng Simulation đọc ở tick tiếp theo. Ngược lại, khi luồng Simulation tính xong một tick và có dữ liệu cần gửi cho client (snapshot, sự kiện), nó đẩy dữ liệu đó vào hàng đợi Output để luồng Network I/O lấy ra và thực sự gọi sendto().

Vì sao cần tách biệt bằng hàng đợi

Lý do cốt lõi: dù socket UDP non-blocking hiếm khi thực sự "chờ lâu", vẫn luôn tồn tại độ trễ hệ thống không thể loại bỏ hoàn toàn — thời gian hệ điều hành xử lý ngắt (interrupt) mạng, thời gian copy dữ liệu giữa buffer kernel và user-space, biến động lịch trình (scheduling) của hệ điều hành khi có nhiều tiến trình/luồng khác cùng chạy trên máy. Nếu luồng simulation trực tiếp gọi recvfrom()/sendto() ngay trong vòng lặp tick của chính nó, bất kỳ độ trễ bất thường nào ở tầng I/O — dù nhỏ — cũng trực tiếp làm trễ nhịp tick vốn cần chính xác và đều đặn của toàn bộ simulation. Tách hai luồng bằng hàng đợi đảm bảo luồng simulation luôn chạy theo đúng nhịp tick của chính nó, hoàn toàn độc lập với bất kỳ biến động nào ở tầng mạng.

C++ — hang doi an toan luong don gian dung giua 2 luong
#include <queue>
#include <mutex>
#include <vector>
#include <cstdint>

struct RawPacket {
    std::vector<uint8_t> data;
    sockaddr_in fromAddr;
};

// Hang doi an toan luong toi gian, dung mutex bao ve - du dung cho quy mo vua/nho.
// Voi luu luong rat cao, co the thay bang lock-free queue chuyen dung.
template<typename T>
class ThreadSafeQueue {
public:
    void Push(T item) {
        std::lock_guard<std::mutex> lock(mutex_);
        queue_.push(std::move(item));
    }

    // Lay het moi phan tu dang co san, khong block neu rong
    std::vector<T> DrainAll() {
        std::lock_guard<std::mutex> lock(mutex_);
        std::vector<T> result;
        while (!queue_.empty()) {
            result.push_back(std::move(queue_.front()));
            queue_.pop();
        }
        return result;
    }

private:
    std::queue<T> queue_;
    std::mutex mutex_;
};

ThreadSafeQueue<RawPacket> g_inputQueue;   // Network thread -> Simulation thread
ThreadSafeQueue<RawPacket> g_outputQueue;  // Simulation thread -> Network thread
C++ — vong lap luong Network I/O
void NetworkThreadLoop(socket_t udpSocket, std::atomic<bool>& running) {
    while (running.load()) {
        // 1. Doc het goi tin dang cho (non-blocking, chuong 9)
        char buffer[1200];
        for (;;) {
            sockaddr_in fromAddr{};
#ifdef _WIN32
            int fromLen = sizeof(fromAddr);
#else
            socklen_t fromLen = sizeof(fromAddr);
#endif
            int n = recvfrom(udpSocket, buffer, sizeof(buffer), 0,
                              (sockaddr*)&fromAddr, &fromLen);
            if (n <= 0) break;   // het goi dang cho hoac loi that

            RawPacket pkt;
            pkt.data.assign(buffer, buffer + n);
            pkt.fromAddr = fromAddr;
            g_inputQueue.Push(std::move(pkt));
        }

        // 2. Gui het du lieu ma luong simulation da chuan bi san
        for (auto& outPkt : g_outputQueue.DrainAll()) {
            sendto(udpSocket, (const char*)outPkt.data.data(), (int)outPkt.data.size(), 0,
                   (const sockaddr*)&outPkt.fromAddr, sizeof(outPkt.fromAddr));
        }

        // Nghi ngan de tranh vong lap "nong" chiem 100% mot loi CPU khi khong co gi de lam;
        // co the thay bang epoll/WSAPoll voi timeout ngan de phan ung nhanh hon (chuong 14/15
        // bo tai lieu Mang may tinh da trinh bay day du hai co che nay)
        std::this_thread::sleep_for(std::chrono::milliseconds(1));
    }
}
C++ — vong lap luong Simulation (tick co dinh, doc/ghi qua hang doi)
void SimulationThreadLoop(std::atomic<bool>& running) {
    const double tickInterval = 1.0 / 20.0;

    while (running.load()) {
        double frameStart = GetTimeSeconds();

        // 1. Lay het goi tin da nhan tu luong Network, ap dung vao simulation
        for (auto& pkt : g_inputQueue.DrainAll()) {
            ApplyIncomingPacketToSimulation(pkt);
        }

        // 2. Tinh mot buoc simulation co dinh
        StepSimulation(tickInterval);

        // 3. Chuan bi du lieu can gui, day vao hang doi Output cho luong Network gui thay
        for (auto& outPkt : BuildOutgoingSnapshots()) {
            g_outputQueue.Push(outPkt);
        }

        double elapsed = GetTimeSeconds() - frameStart;
        double sleepTime = tickInterval - elapsed;
        if (sleepTime > 0) {
            std::this_thread::sleep_for(std::chrono::duration<double>(sleepTime));
        }
    }
}

2. Nhưng: Game Logic gần như luôn nên chạy đơn luồng

Đây là điểm dễ gây hiểu lầm nhất khi mới tiếp cận kiến trúc đa luồng: nhìn thấy hai luồng ở trên, nhiều người mới có xu hướng nghĩ tiếp "vậy có nên chia nhỏ luồng Simulation thành nhiều luồng song song nữa để tận dụng tối đa CPU đa nhân?" — ví dụ một luồng tính vật lý, một luồng tính AI, một luồng khác xử lý va chạm, chạy đồng thời.

Vì sao song song hóa toàn bộ game logic là một cạm bẫy: Trạng thái thế giới game (world state) có quan hệ chằng chịt giữa các entity — một vụ va chạm có thể ảnh hưởng đồng thời tới vị trí, sức khỏe, animation, và cả AI của nhiều entity khác nhau cùng lúc; một hành động của người chơi này có thể kích hoạt logic liên quan tới hàng chục entity khác trong cùng một tick. Nếu để nhiều luồng cùng đọc/ghi trực tiếp vào world state dùng chung, chương trình rơi vào chính những vấn đề kinh điển và khét tiếng khó debug nhất của lập trình đa luồng: race condition (hai luồng cùng đọc/ghi một biến mà không đồng bộ, kết quả phụ thuộc thứ tự thực thi ngẫu nhiên), deadlock (hai luồng cùng chờ khóa (lock) của nhau, không luồng nào tiến triển được), và các lỗi chỉ xuất hiện ngẫu nhiên, không lặp lại được (non-deterministic bug) cực kỳ tốn thời gian tìm ra nguyên nhân gốc rễ.

Vì vậy, kiến trúc an toàn và dễ suy luận hơn hẳn mà phần lớn game server thành công trong thực tế lựa chọn — kể cả những server quy mô lớn phục vụ hàng nghìn người chơi đồng thời — là: đơn luồng cho toàn bộ game logic (world state chỉ có đúng một luồng được phép đọc/ghi trực tiếp, loại bỏ hoàn toàn khả năng race condition ở tầng logic), kết hợp với đa luồng/bất đồng bộ chỉ cho tầng I/O (nơi công việc — đọc/ghi socket — độc lập tự nhiên với nhau và không đụng chạm trực tiếp tới world state).

Cùng triết lý với các engine thương mại lớn:
  • Unity: toàn bộ vòng lặp game logic chính (MonoBehaviour.Update(), vật lý, xử lý sự kiện) chạy trên một main thread duy nhất — dù Unity có cung cấp Job System và Burst Compiler để song song hóa các tác vụ tính toán nặng, tách biệt và có kiểm soát chặt chẽ (ví dụ tính toán mảng dữ liệu độc lập, không có quan hệ chằng chịt), chứ không phải song song hóa bừa toàn bộ world state.
  • Unreal Engine: có một Game Thread chính duy nhất chạy gameplay logic và xử lý replication mạng, trong khi rendering, audio, và một phần physics chạy trên các luồng riêng biệt được đồng bộ hóa cẩn thận ở những điểm ranh giới rõ ràng (ví dụ cuối mỗi frame) — không phải song song hóa gameplay logic một cách tùy tiện.
Cả hai engine hàng đầu ngành đều đi tới cùng một kết luận kiến trúc: giữ gameplay logic đơn luồng để dễ suy luận và không có race condition, chỉ song song hóa những phần công việc tách biệt rõ ràng khỏi world state chính (I/O mạng, rendering, một số tính toán nặng độc lập).

Tổng kết chương

Kiến trúc chuẩn cho game server: tách luồng Network I/O (đa luồng/non-blocking, giao tiếp qua hàng đợi an toàn luồng) khỏi luồng Simulation (đơn luồng, tick cố định) để vừa tận dụng được I/O multiplexing hiệu quả, vừa giữ world state hoàn toàn tránh được race condition. Đây không phải một giải pháp "tạm thời vì chưa tối ưu" mà là lựa chọn kiến trúc có chủ đích, được chứng minh qua cách cả Unity lẫn Unreal Engine tổ chức vòng lặp chính của chúng. Chương 14 sẽ hiện thực hóa toàn bộ kiến thức của Phần II — packet header, non-blocking loop, reliable UDP tối giản, heartbeat/timeout, và cấu trúc luồng vừa học — thành một ví dụ game server UDP hoàn chỉnh, biên dịch chạy được.
